## IV-S-1: The skill tells agents to check the signature before any rebuild

**Category:** bug. **Status:** done 2026-10-15 (commit `9b9fd13`; DD-S-1 `027e7bf`). **Priority:** P2. **Blocked by:** DD-S-1 (same documents; the versioned contract lands first so this edit goes into both served versions once).

The skill document tells an agent that a built transaction expires in about ninety seconds and to "rebuild instead of retrying a stale one". It never tells the agent to first check whether the transaction it already submitted landed. For a trade the cost of getting that wrong is a second swap. For a launch it is worse: every `/api/launch` call generates a fresh mint keypair, re-pins the image and metadata, and returns a transaction that creates a new pool with the first buy attached, so an agent that submits, times out on confirmation, and "rebuilds" mints a duplicate token and pays the creation fee plus the first buy twice. Nothing in the document asks the agent to confirm the amounts with its user before signing, to persist the signature and mint address before sending, or to confirm the signature after sending; the error table marks upstream failures "safe to retry" without that qualification. Evidence: `SKILL.md` (Transactions — signing and expiry; Error shapes), `public/skill.json`, `src/app/api/launch/route.ts` (fresh mint per call), the update branch's `src/lib/dbc-launch.ts` and `src/lib/first-buy.ts`.

Done when:
- [x] The launch and trade build responses gain an additive optional `lastValidBlockHeight` field taken from the same `getLatestBlockhash` call that supplied the blockhash (the builders currently keep only the blockhash), so an agent can prove expiry; no other shape change.
- [x] The signing-and-expiry section states the submit protocol in order: persist the signature (and for a launch the `mintAddress`) before broadcasting; after broadcasting, poll signature status with transaction-history search; a finalized success is done (reuse the recorded `mintAddress`, never relaunch); a finalized failure means the transaction landed and failed, so a rebuild is safe; an absent status is "not landed yet" only once a finalized block-height read exceeds the response's `lastValidBlockHeight` **and** one more history search after that read still finds nothing, in that order; an RPC error at any step leaves the outcome unknown. Without a `lastValidBlockHeight` (older cached docs, or a response that lacks it) the outcome cannot be proven and the agent must not rebuild automatically: it reports the signature to its user and waits. It states in one sentence that a launch rebuild creates a new mint and pool and spends again, so a rebuild after an unknown outcome is a duplicate-token hazard.
- [x] The error table's "safe to retry" entries say "safe to re-request a build; see the submit protocol before re-sending", and the `409 pool_not_tradeable` / `503` retry guidance keeps its existing wording.
- [x] A short "before signing" line asks the agent to show its user the amount, the quote asset and (for a launch) the first-buy amount in that asset, and to confirm, matching the amounts the response already returns; no endpoint shape changes.
- [x] `skill.json` carries the same protocol text wherever it mirrors the signing section, and the DD-S-1 agreement test passes on both served versions; the landing page that mirrors `SKILL.md` (from the update branch) shows the same text.
